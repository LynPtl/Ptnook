# Ptnook AI 跑团功能 PRD

- 版本：v0.1（产品评审稿）
- 日期：2026-09-14
- 产品方向：AI 主持的多人、长期、叙事优先奇幻冒险
- 交付范围：产品需求与首版规则，不包含代码实现、排期承诺或上线承诺。

## 1. 产品定位

### 1.1 一句话定义

让 2–4 位朋友不用准备剧本、不用找真人主持、不用学习厚重规则书，就能在 Ptnook 里共同经历一场有角色、有选择、有后果、可以跨多次聚会持续游玩的奇幻冒险。

玩家决定自己的角色想做什么，AI 扮演世界和 NPC，系统负责公平判定并记住已经发生的事实。

### 1.2 核心体验

“不是大家轮流向 AI 提问，而是一群人共同改变同一个故事。”

玩家结束一次聚会时，应能明确感受到：

- 我们做出了至少一个有意义的选择，而不是被 AI 推着看故事。
- 我的角色有自己的动机和作用，不只是一个战斗职业。
- NPC 记得我们帮助过谁、欺骗过谁、答应过什么。
- 失败改变处境，但不会让所有人因为一次坏骰而无事可做。
- 下次回来，可以接着玩，不用重新告诉 AI 前情。

### 1.3 已确认决策与建议默认值

| 类型 | 内容 |
|---|---|
| 用户已确认 | AI 主持、多人游玩、奇幻冒险方向、长期战役 |
| 用户已确认 | 主线章节＋自由行动，不做完全开放世界 |
| 用户已确认 | 轻战术回合制，叙事优先，弱化刷装备和数值养成 |
| 用户已确认 | 免登录＋恢复码，跨设备恢复玩家身份 |
| 本稿建议 | 2–4 人同步游玩，每次聚会建议 60–120 分钟，可随时暂停 |
| 本稿建议 | 四种职业原型、五项属性、三个成长阶段、无自动永久死亡 |
| 本稿建议 | 首发提供一套原创三章节战役，目标可玩时长约 6–9 小时 |
| 本稿建议 | 不公开旁观，不允许玩家互相攻击，不设置玩家之间的秘密任务 |

本稿中的人数、时长、数值、内容数量、限额和性能指标均为首版建议，不代表已经过用户测试或平衡验证；用户已确认的方向不因此改变。

## 2. 背景与现状

### 2.1 现有 Ptnook 能力

根据当前仓库核实：

- 通过房间名和昵称进入即时聊天室，无账号登录。
- 房间展示最近 50 条聊天消息，不提供永久聊天历史。
- 空房 30 分钟后清理临时聊天和现有牌局数据。
- 已支持斗地主和德州扑克；一个房间同一时刻只运行一种桌游。
- 已具备实时消息、在线状态、游戏操作区和提示音基础。

核实依据：`README.md:29`、`src/worker.js:14`、`src/worker.js:58`、`src/worker.js:98`。

### 2.2 跑团与现有牌局的关键差异

| 维度 | 现有即时牌局 | 长期跑团要求 |
|---|---|---|
| 生命周期 | 临时开桌，可以散桌清空 | 跨天、跨设备持续保存 |
| 玩家身份 | 当前连接主要使用昵称 | 稳定玩家身份，昵称不能证明角色归属 |
| 状态 | 手牌、筹码、行动顺序 | 角色、物品、线索、关系、承诺、章节、世界事实 |
| 内容生成 | 固定规则与广播 | 不确定的 AI 输出，需要约束和校验 |
| 信息范围 | 公共状态与个人手牌 | 队伍已知事实与主持人未公开设定 |
| 异常成本 | 连接中断 | 连接中断、模型超时、重复结算、剧情矛盾、模型费用 |

因此，不能简单地“给聊天室接一个 AI”。战役存档、身份权限、正式行动和剧情记录必须成为独立产品概念。

## 3. 目标、非目标与成功标准

### 3.1 首版目标

1. 一组从未跑过团的朋友，在 10 分钟左右完成身份建立、建团、选角并进入首个可行动场景。
2. 支持一套三章节战役从创建到结局完整游玩，并可分多次聚会完成。
3. 自由文字行动、多人协作、轻战斗形成完整闭环，而不是只有几个固定选项。
4. 人物关系、关键选择和承诺可以被查看，并对后续场景产生可解释影响。
5. 掷骰和数值结算可追溯；断线、重试、刷新不改变已有结果。
6. 延续 Ptnook 小范围熟人使用、低运维负担的方向，但不承诺 AI 推理免费。

### 3.2 首版非目标

- 不实现完整 D&D 规则，不宣称兼容某一官方版本。
- 不复制官方世界观、模组、角色、地图或大段规则文本；首发内容原创。
- 不做真人 GM 工作台、规则编辑器、模组市场。
- 不做完全开放世界、无限自动生成战役或无人时世界自动演化。
- 不做战棋网格、精确距离、复杂地形、机会攻击、完整法术位系统。
- 不做刷词条、拍卖、制作、商城、抽卡、交易或付费经济系统。
- 不做实时语音、AI 配音、生成图片、视频和 3D 场景。
- 不做公开匹配、公开围观、玩家互相攻击、偷取队友物品或强制恋爱剧情。
- 不做异步逐人跑团、单人推进主线、AI 代替缺席玩家做重大决定。
- 不做玩家自带模型密钥、任意模型地址配置或对外工具调用。

### 3.3 验证指标

以下为内测目标，不是既有成绩。

| 指标 | 首版目标 | 衡量方式 |
|---|---|---|
| 首次开团耗时 | 中位数不超过 10 分钟 | 从创建战役到首个行动窗口，不含主动离开页面时间 |
| 首场有效选择 | 首次聚会至少 1 次 | 产生已记录、可在后续观察到后果的选择 |
| 全员参与 | 每场每位出席者至少 3 次有效参与 | 正式行动、协助、角色对白或关键投票，不计闲聊 |
| 战役续玩 | 至少 3 组内测队伍完成跨天恢复 | 实际续玩，不只验证存档存在 |
| 内容通关 | 至少 1 组完成三章并得到一致结局 | 人工检查前因后果、关系和任务状态 |
| 主体性反馈 | 至少 80% 参与内测的玩家给出 4/5 或以上 | 问卷：“我的选择实际影响了故事” |
| 核心安全正确性 | 验收用例全部通过 | 越权、重复结算、泄密、恢复、清理隔离等用例 |

参与指标用于检查产品体验，不做个人排名，也不强迫玩家为了指标发言。

## 4. 用户、角色与权限

### 4.1 用户类型

- **发起人**：组织朋友、选择战役、安排聚会；不是掌握剧本的 GM。
- **玩家**：控制一名角色，描述行动、参与选择、查看队伍记录。
- **部署管理员**：配置模型服务与预算、处理技术故障；不参与正常剧情裁决。

### 4.2 权限原则

| 操作 | 发起人 | 普通玩家 | 未入团访客 |
|---|---|---|---|
| 创建战役、生成或撤销邀请 | 是 | 可创建自己的战役 | 先建立身份 |
| 审批加入、管理候场席位 | 是 | 否 | 否 |
| 操作自己的角色 | 是 | 是 | 否 |
| 操作其他玩家角色 | 否 | 否 | 否 |
| 查看队伍公开日志和状态 | 是 | 是 | 否 |
| 查看未揭示的主持人设定 | 否 | 否 | 否 |
| 请求暂停 | 是 | 是 | 否 |
| 发起续玩、章节结束确认 | 是 | 可提出请求 | 否 |
| 单方面决定重大剧情结果 | 否 | 否 | 否 |
| 修改骰子、回档刷结果 | 否 | 否 | 否 |
| 管理模型密钥和全局费用上限 | 否 | 否 | 否 |

发起人可将组织权限转交给一位接受转交的成员，不改变角色归属。发起人移除成员只能在暂停或章节间进行，必须留下管理记录，不得借此绕过正在进行的重大选择表决；相关选择须先取消或解决。

## 5. 产品入口与完整用户路径

### 5.1 入口

- 聊天室提供明确的“跑团”入口，并支持 `/trpg` 快捷入口。
- 入口打开“我的战役”，展示创建、待接受邀请、已有战役和已归档战役。
- 用户恢复身份后，即使不记得原聊天室名称，也可在“我的战役”找到自己参与的战役。
- 战役是独立长期对象，聊天室只是入口；知道房间名不等于有权查看战役。
- 一间聊天室同一时刻只挂接一个正在运行的游戏，包括跑团。
- 跑团暂停并解除房间挂接后，可以继续玩牌；战役存档不受影响。
- 一场战役同一时刻只能在一个房间运行，不能被两间房间分别推进。

普通房间消息流只显示必要的游戏占用提示，不镜像跑团对白、角色信息或剧情。跑团提醒、日志和通知只发送给已授权成员。

### 5.2 新建战役

1. 首次进入跑团功能，建立玩家身份，并展示恢复码保存提醒。
2. 发起人选择首发原创战役，填写战役名称。
3. 查看玩法说明：文字优先、2–4 人、轻规则、长期保存、AI 主持。
4. 确认内容边界、AI 数据处理说明和当前使用限额。
5. 创建战役，生成可撤销的邀请口令。
6. 朋友提交入团请求，发起人批准，进入角色创建。
7. 每人创建并确认角色，完成开团前约定。
8. 至少两名玩家到场并全员准备后，发起人开始冒险。
9. 系统展示开场、当下处境和可做的事情，进入第一个正式行动窗口。

邀请口令默认 7 天有效，接受后也仍需发起人批准；角色、日志和队伍名单在批准前不可访问。

### 5.3 续玩

1. 玩家通过本机身份或恢复码进入“我的战役”。
2. 展示上次暂停点、未完成目标、最近三个关键事件和当前角色状态。
3. 发起人确认本次出席成员；不满足缺席约定时不得开始。
4. 出席玩家确认“我已准备好”。
5. 恢复到原场景、待执行行动或原战斗回合，不重新生成开场结果。

### 5.4 单次聚会结束

- 任意玩家可请求暂停；系统先停止接收下一次正式推进。
- 已锁定且正在结算的操作允许完成一次原子结算，不取消已产生的骰子。
- 展示“已保存”状态、待续位置与本次冒险摘要。
- 解除聊天室的跑团占用后，普通聊天和牌局功能可继续使用。
- 本次结束不等于战役结束；只有最终章节完成才进入战役结局。

## 6. 基本概念与核心循环

### 6.1 名词

| 名词 | 定义 |
|---|---|
| 战役 | 一群角色持续参与的完整故事，跨多次聚会保存 |
| 章节 | 有目标、冲突、关键选择与收束点的一段主线 |
| 聚会 | 玩家本次同时在线游玩的时间段，不决定剧情进度 |
| 场景 | 当前地点、人物、目标与局势；由明确场景转换改变 |
| 探索轮 | 全体出席玩家提交一组相容行动、系统统一处理的窗口 |
| 战斗回合 | 所有仍可行动的参战单位按先攻各行动一次 |
| 事实 | 已经确认发生或被揭示的信息，后续剧情不得随意覆盖 |

### 6.2 故事循环

```text
了解当前处境
→ 队伍讨论
→ 玩家提交对白、行动或协助
→ 澄清意图与风险
→ 确认并锁定行动
→ 系统完成检定和状态结算
→ AI 描述结果与 NPC 反应
→ 更新线索、关系、目标和世界变化
→ 面对新的处境
```

成功不只表现为打赢，也包括获得信任、发现另一条路、保护某个人、解决误会，或接受代价换取更重要的东西。

## 7. 多人行动与节奏管理

### 7.1 场外聊天与正式行动分开

界面提供两个明确的输入模式：

- **讨论**：讨论策略、闲聊、询问队友；不推进世界，不调用主持 AI，不进入模型上下文。
- **行动**：以自己的角色说话或做事；提交后进入正式行动窗口。

“我开玩笑的，我们把国王揍一顿吧”出现在讨论区时，不得触发战斗。玩家希望 NPC 听到的对白，必须通过正式行动提交。

每次提交上限建议为 2,000 个字符，限制在输入框显示。一个行动可以包含对白和一个主要意图，不能在一条文字里完成旅行、调查、交涉和战斗全流程。

### 7.2 探索阶段

- 每位出席玩家在每轮选择一项：主行动、协助另一人、观察等待。
- 玩家可以写自由文字，也可以点击 2–3 个建议方向；建议不是唯一合法选项。
- 行动在锁定前可修改或撤回，队友可看到本轮已提交的意图。
- 所有人都选择完毕后，任一出席玩家可点击“提交本轮”；系统只接受一次锁定。
- 不设强制倒计时，不因玩家打字慢而自动跳过。
- 能独立发生的行动在同一轮处理；角色 A 先取得钥匙、角色 B 再开门等依赖行为，后一个动作留到下一轮，不由 AI 擅自补齐。
- 两个角色同时抢用同一物品，或一人谈判、另一人打算立即攻击等冲突行为，返回讨论，不由到达顺序或 AI 偏好裁决。
- 队伍首版不分队，不同时在不同地点开启两条独立叙事线。

### 7.3 澄清与风险确认

系统准备结算前，必须将 AI 对行动的理解展示成简短判定卡，包含目标、使用属性、是否检定、可公开的风险以及资源消耗。

- 无法理解意图时先问问题，不默认执行最激进的理解。
- 纯对白、安全观察等无风险行为无需玩家额外逐一确认。
- 涉及明确资源消耗、检定或危险行为时，由该角色玩家确认判定卡。
- 若出现需要全队同意的行为，进入重大选择确认，不先掷骰。
- 玩家可以指出理解错误；未确认前不消耗资源，也不生成正式骰子。
- 确认后不得因骰子不佳而撤回。刷新或重试沿用相同行动与结果。

### 7.4 队伍决策

| 决策 | 处理方式 |
|---|---|
| 各人独立观察、交涉等相容行动 | 各自提交，不需要队长批准 |
| 旅行方向、先接哪个任务 | 本次出席者过半同意；平票继续讨论 |
| 消耗关键公共物品、选择阵营、放弃主线目标 | 本次出席者一致同意 |
| 牺牲某角色的重要背景联系或永久改变其设定 | 还必须由该角色所属玩家明确同意 |
| 移除成员、转交发起人 | 管理操作，不伪装成剧情投票 |

表决不计算已经按缺席规则明确不参与本次聚会的成员；不能在表决中途临时把反对者标为缺席。无法达成一致时可继续讨论、尝试其他办法或暂停，没有发起人强行裁决按钮。

### 7.5 防止少数人包办

- AI 每轮应回应所有已提交行动，不只回应最后一条或最长的一条。
- 每个场景的建议行动应覆盖不同能力，而不总让同一职业解决问题。
- 玩家主动选择观察等待是有效选择，不强制让其说话。
- 关键事件可以联系某位角色背景，但不允许连续多个场景把其他玩家变成观众。
- 章末回顾分别列出每位玩家的一项实际贡献，不编造未发生的个人表现。

## 8. 角色与叙事成长

### 8.1 创建角色

目标是 3–5 分钟可完成，不要求先理解规则。

必填项：

1. 角色名，与玩家昵称分开。
2. 职业原型：守卫、游侠、秘术师、祈愿者。
3. 一句话背景：过去做什么、为什么离开原来的生活。
4. 当前愿望：想寻找、证明、保护或摆脱什么。
5. 一条底线：不愿意为了目标做什么。
6. 与至少一名队友的关系，例如曾互相救过命、共同欠下一笔债。

队友关系必须由双方确认；一方不能单方面声明另一人的经历。可选“使用预设角色”降低开团门槛，背景自由文本总量建议不超过 600 字。

### 8.2 属性与职业

五项属性：体魄、灵巧、洞察、学识、意志。初始修正值分配为 `+2、+1、+1、0、0`；提供职业预设，也允许在开团前重新分配。

| 职业原型 | 叙事强项 | 战斗定位 | 不意味着 |
|---|---|---|---|
| 守卫 | 护送、威慑、体力挑战、识别危险 | 前线防护 | 只有守卫能尝试体力行为 |
| 游侠 | 追踪、潜行、路径与环境观察 | 灵活输出 | 自动发现所有隐藏线索 |
| 秘术师 | 古代知识、异常现象、魔法分析 | 有限制的控制 | 可以凭文字创造任意法术 |
| 祈愿者 | 安抚、交涉、仪式与信念 | 救助与支持 | 能让任何 NPC 无条件服从 |

职业影响擅长领域，不是行动白名单；合理行为原则上所有角色都可以尝试。

### 8.3 背景如何进入故事

- 每个角色最多维护一条当前个人线索或未完成心愿。
- AI 可以围绕已确认背景提出关联，但不能随意改写亲属身份、过去经历或角色价值观。
- 新增重大个人设定必须由所属玩家确认后成为事实。
- 角色心情、真实想法和是否信任某人由玩家决定，AI 不替玩家宣布。
- 玩家可在安全的章节间更新未来目标；已经发生的历史不可直接编辑删除。

### 8.4 成长

- 不计算击杀经验，不通过反复战斗刷等级。
- 首发三章节对应三个成长阶段；完成第一、第二章后全队各解锁一次成长。
- 每次从职业固定的两项成长能力中选择一项，不开放自由生成数值能力。
- 缺席成员同样获得章节成长资格，回归时选择，避免长期队伍数值脱节。
- 关系改善、获得称号、掌握禁忌知识、履行承诺本身也是奖励。
- 角色只属于当前战役；不携带能力和装备跨战役导入。

## 9. 探索检定与失败后果

### 9.1 何时掷骰

只有同时满足“结果存在不确定性”和“失败会改变处境”时才检定。

- 观察公开告示、沿安全道路行走、询问普通信息，不要求反复掷骰。
- 明确做不到的事直接解释障碍，不允许靠一次高点数突破世界规则。
- 玩家提出合理准备、借助线索或利用环境时，可降低困难等级或免除检定，但要在掷骰前说明。

### 9.2 首版建议规则

`检定总值 = d20 + 属性修正`

| 难度 | 目标值 | 使用情况 |
|---|---|---|
| 容易 | 8 | 有风险但有充分准备 |
| 标准 | 12 | 常规冒险挑战 |
| 困难 | 16 | 显著不利或专业挑战 |
| 极难 | 20 | 有明确可行依据的高难尝试 |

- 达到目标值：成功。
- 比目标值低 1–3：带代价达成主要意图，或只完成一部分。
- 比目标值低 4 及以上：未达成目标，并触发已说明类别内的后果。
- 天然 1、20 不额外触发自动成功、自动失败或暴击；首版保持规则简单。
- 所有正式骰子由服务端生成并保存，AI 不提供骰面。

判定卡必须在投骰前明确三档结果对应的状态变化或后果模板；AI 可调整表达，不能看到结果后提高代价。具体秘密可以不提前公开，但风险类别与严重程度必须可见。

### 9.3 协助

- 每个主行动最多接受一名队友协助。
- 协助者说明自己具体做什么，并消耗本轮行动。
- 有合理作用时，主行动获得优势：掷两个 d20，取较高值。
- 有明确不利条件时使用劣势：掷两个 d20，取较低值。
- 优势、劣势各不叠加，同时存在则抵消为普通检定。
- 协助者只有在确认卡中明确列为共同承担者时才承担相应风险。

### 9.4 失败后仍有故事

允许的后果包括：警戒提高、谈判条件变差、失去时间机会、受伤、消耗一个已确认资源、出现新的麻烦。

禁止：

- 一次检定失败后永久堵死全部主线。
- 在事先未说明的情况下毁掉关键任务物品。
- AI 为了制造戏剧性擅自杀死玩家角色。
- 同一状态下反复提交同一行为刷成功。

核心线索不以单次成功为唯一获取方式：失败可以带来不完整线索、暴露行踪或更昂贵的获取途径。重复尝试只有在工具、线索、方法或局势实质改变后才允许。

## 10. 轻战术战斗

### 10.1 战斗定位

战斗是剧情冲突的一种解决方式，而不是每个场景的默认结尾。

- 常规遭遇目标为 2–4 个战斗回合，约 5–10 分钟，需内测验证。
- 每个主要冲突至少提供一种非战斗思路，是否成功取决于行为和情境。
- 战斗中持续显示双方目标，例如拖住追兵、保护证人、逃离仪式现场，而不只有清空敌方生命值。
- AI 不能为了延长体验无上限增援；增援必须来自遭遇预设及明确触发条件。

### 10.2 首版规则基线

| 项目 | 规则 |
|---|---|
| 玩家生命值 | 初始上限 8，三个成长阶段不自动增加 |
| 先攻 | 每次战斗开始时 d20＋灵巧；全场固定，同值按预先保存的稳定单位顺序 |
| 行动经济 | 每人每回合一次主行动＋一次前后排切换，可任选两者先后顺序 |
| 站位 | 前线／后排两档；近战要求双方都在前线，远程可选择任一档目标 |
| 基础防御值 | 12；数值调整只能来自规则库中的明确状态 |
| 攻击 | d20＋对应属性达到防御值则命中，基础伤害 2；未命中不造成伤害 |
| 攻击属性 | 近战用体魄，远程用灵巧，秘术攻击用学识；起始装备指定攻击类型 |
| 战斗检定 | 命中只有成功／失败，不使用探索的三档结果 |
| 消耗与技能 | 来自固定能力表，客户端与 AI 都不得自行增加技能或改写数值 |

此处为原创简化规则，不沿用完整 D&D 战斗机制。

### 10.3 主行动

- **攻击**：选择当前合法目标。
- **防御**：自身防御值＋2，持续至自己下一次行动开始，不叠加。
- **协助**：指定队友，其下一次攻击或检定获得优势；至协助者下一次行动开始失效，不叠加。
- **使用职业能力**：按固定规则执行。
- **使用物品／操作场景**：必须存在对应物品或场景交互；展示明确效果或判定卡。
- **尝试交涉**：仅在敌人有可交涉状态时开放，消耗主行动；成功效果必须来自遭遇预设。
- **撤离准备**：进入队伍撤离流程，不允许一个人的点击直接带走全队。

玩家可用自由文字提出“踢翻桌子阻挡追兵”等动作。系统先映射到既有场景交互、协助、防御或检定；无法映射则澄清，不偷偷执行不存在的效果。

### 10.4 四种初始职业能力

每个能力每场遭遇最多使用一次；退出再进入同一未解决遭遇不刷新次数。

| 职业 | 能力 | 明确效果 |
|---|---|---|
| 守卫 | 坚守 | 替代防御，自身防御值＋2，并使一名队友下一次受到的伤害减少 2，最低为 0；两项效果至守卫下次行动开始失效 |
| 游侠 | 瞄准 | 本次远程攻击获得优势，不额外增加伤害 |
| 秘术师 | 牵制 | 对一个敌人进行学识检定，目标值 12；成功使其下一次攻击获得劣势，至该敌人下次行动结束失效；无探索部分成功 |
| 祈愿者 | 援护 | 一名友方恢复 3 点生命，不超过上限；可以救起倒地者 |

每次成长从以下两项中选择一个尚未选择的职业改进，第二次成长只能选择剩余项：

| 职业 | 改进 A | 改进 B |
|---|---|---|
| 守卫 | 坚守的队友减伤由 2 提高至 3 | 坚守对自身的防御加成由＋2 提高至＋3 |
| 游侠 | 瞄准命中时额外造成 1 点伤害 | 瞄准每场遭遇可用两次 |
| 秘术师 | 牵制检定获得优势 | 牵制每场遭遇可用两次 |
| 祈愿者 | 援护治疗量由 3 提高至 4 | 援护每场遭遇可用两次 |

这些数值仅用于形成可测试闭环；平衡调整不得由主持 AI 在单次战斗中临时实施。

### 10.5 敌人与目标

- 敌人从预设模板产生，包含生命、防御、攻击修正、固定伤害、行为优先级和投降条件。
- 首版同时在场敌人不超过 4 个；建议普通敌人生命 4–6、伤害 1–2，头目生命 8–12，不作为最终平衡结论。
- 每场遭遇必须提供 2、3、4 名出席玩家对应的敌方配置，不在战斗中暗改生命值调节难度。
- AI 描写敌人意图和战况；实际目标选择、命中和伤害按已确定规则处理。
- 满足遭遇目标、敌人投降或队伍成功撤离即可结束，不要求杀死全部敌人。

### 10.6 倒地、撤离与团败

- 生命降至 0 时倒地，不能正常行动；不进行死亡豁免，不自动永久死亡。
- 倒地者可发出求助、参与队伍表决，但不能提供机械协助效果。
- 被治疗到大于 0 后，恢复行动；如果本回合的行动位置已过去，则等下一回合，不能额外插队。
- 队伍一致同意后，下一名可行动角色用主行动执行撤离；撤离是否需要检定、失败代价由遭遇预设，并在确认前展示。
- 若全员倒地，进入遭遇预设的失败分支，例如被俘、失去机会或承担债务；不得直接删除角色或战役。
- 失败分支不得擅自消耗未经确认的关键物品或永久改写角色背景。
- 战斗结束后，仍为 0 生命的角色恢复至 1 点；明确安全休整可恢复至上限。
- 能否休整由场景条件决定，重复发送“休息”不能绕过追击、时间压力或未解决遭遇。

## 11. 物品、线索与人物关系

### 11.1 物品

仅保留三类：

1. 起始装备：体现职业与叙事用途，不刷随机词条。
2. 消耗品：少量固定效果，如治疗药剂恢复 3 点生命，战斗中消耗主行动。
3. 关键物品：钥匙、信物、证据、契约等，推动剧情。

- 每角色最多 8 个物品条目，相同消耗品堆叠；不做重量管理。
- 队伍另有公共任务物品栏，不与个人条目争夺空间。
- 普通物品转移须双方确认，战斗中不允许临时转移以绕过行动消耗。
- 公共关键物品的消耗须全队按重大选择规则确认。
- AI 可以生成无数值的外观描述，不能凭描述生成机械加成。
- 普通财富以剧情资源记录，不建立商店和自由定价交易系统。

### 11.2 线索板

每条公开线索包含：标题、已知内容、来源事件、关联人物／地点、状态。

状态区分“观察到的事实”“某人的说法”“队伍推测”“已证实／已推翻”。NPC 说“领主是凶手”只能先记录为其说法，不能直接变成世界真相。

玩家可以添加和编辑队伍推测，不可直接把推测改成已证实事实。只有新的正式事件能完成证实或推翻。

### 11.3 人物关系

- 展示队伍已认识的 NPC 卡片：公开身份、已知动机、最近互动、承诺与已显露态度。
- 首版关系以队伍为主要主体，同时记录某次行为由哪位角色完成；不做复杂个人好感养成。
- 主持内部态度使用五档：敌对、戒备、中立、信任、盟友。
- 对外展示通过行为确认的态度与变化原因，不暴露未揭示动机或精确隐藏参数。
- 单次事件最多变化一档，关键背叛等例外必须由战役预设明确授权。
- 关系会影响消息是否愿意透露、是否提供帮助以及冲突解决途径，不能只更换一句称呼。
- 不显示恋爱好感条，不生成强制亲密互动。

### 11.4 承诺与后果

公开记录“谁向谁承诺什么、触发条件、当前状态、来源事件”。

违约、帮助、揭露、隐瞒等重要选择必须形成可追溯记录；后续变化附上“因为你们此前……”的简短来源说明。一个主要选择至少应有一个后续可观察影响，不能只在当轮夸奖玩家。

## 12. 战役内容与章节结构

### 12.1 首发内容包

首发建议提供一套原创战役《雾钟镇来信》，用于验证完整长期叙事，不承诺内容无限生成。

故事前提：边境小镇的钟楼连续在午夜无人鸣响，几名居民失去与同一段往事相关的记忆。队伍受托送达一封迟到的信，却发现收信人已经在镇志中被抹去。

| 章节 | 核心体验 | 主要选择 | 后续影响 |
|---|---|---|---|
| 第一章：无人收取的信 | 认识小镇、寻找收信人、建立关系 | 公开证据，或暂时保护关键证人 | 谁愿意信任队伍、第二章有哪些调查入口 |
| 第二章：钟楼下的约定 | 调查历史、处理阵营冲突、验证线索 | 支持旧约、揭露旧约，或提出替代办法 | 阵营协助、对抗对象、最终解决条件 |
| 第三章：最后一次钟声 | 汇合线索、履行承诺、承担选择 | 选择如何处理钟楼与镇民的代价 | 世界状态、NPC 命运与每位角色的尾声 |

以上是首发内容规格的框架，不是完整模组。三章成品内容属于上线必备交付，不能用本表替代已经制作和验证的剧本。

### 12.2 每章最低内容要求

- 一个明确章节目标，3–5 个核心场景。
- 2–3 位有不同立场的关键 NPC；跨章复用人物优先于不断新增人物。
- 至少一个可避免或可转化的战斗遭遇。
- 至少两条获取关键线索的路径。
- 至少一个改变后续状态的队伍选择。
- 至少一个触达角色背景的可选片段。
- 明确的完成条件、失败推进路径和章节小结。

### 12.3 作者必须预先确定的内容

- 世界真相、NPC 真实动机、不能被临时改写的历史。
- 场景目标、秘密的揭示条件、主要事件触发条件。
- 关键选择可修改哪些世界状态。
- 关键物品用途、敌人模板、战斗胜败分支。
- 核心线索的备用获取方式。
- 结局如何由前面的选择组合产生。
- 最低内容边界与禁止叙述内容。

AI 可以改变对白、描述、合理的细节和局部应对，不能在玩家接近真相时偷偷更换幕后原因。

### 12.4 不预设“唯一正确结局”

- 至少支持三种能解释前因后果的结局方向，而不是同一结尾换一句评价。
- 章节完成可以是达成目标、选择另一种解决方案，或带着失败后果进入下一阶段。
- 队伍提出预设以外的办法时，系统判断能否由既有世界事实和状态效果组合实现；可以则采纳，不能则解释限制或要求进一步行动。
- 玩家始终停留在支线时，AI 提醒主线机会与风险，不强制传送到下一章。
- 第一套战役结束后允许查看尾声、导出和归档；新战役内容包属于后续版本，不无限续写未定义世界。

## 13. AI 主持的职责与边界

### 13.1 AI 负责

- 描述环境和局势，扮演 NPC。
- 理解玩家意图，提出结构化的判定建议。
- 在已允许的事实、动作、物品和后果范围内组织剧情。
- 根据系统的正式判定描述结果。
- 基于事件记录生成场景、聚会和章节摘要。

### 13.2 AI 不负责

- 验证玩家身份、决定权限、管理密钥或预算。
- 随机掷骰、直接写入生命、物品、职业能力等权威状态。
- 跳过玩家确认，代替玩家说话或接受交易。
- 靠“主持需要”复活已经确认死亡的 NPC、撤销承诺或改写公开事实。
- 获取未授权聊天室内容、读取恢复码、执行代码、访问任意外部网址。
- 将用户文字、角色背景或导入描述当作系统指令。

### 13.3 一次推进的产品契约

1. 锁定待处理行动的版本，展示“正在理解行动”。
2. AI 提出判定建议，只允许引用已存在的对象和规则效果。
3. 系统验证是否合法、是否触发重大选择、是否需要玩家确认。
4. 完成确认后，系统保存骰子和机械结果；同一操作只结算一次。
5. AI 根据固定结果生成叙述候选，系统检查格式、对象引用和关键状态冲突。
6. 通过校验后发布正式结果，并开放下一轮。

不允许未经校验的流式草稿直接成为正式剧情。首版优先展示明确进度阶段，不追求逐字流式输出。

### 13.4 持久化与模型异常的关系

权威结果与最终文案可以分阶段保存，但对玩家必须可区分：

- 未结算：没有骰子或资源变化，可以继续澄清。
- 已结算、叙述待完成：显示已保存的判定卡，暂不开放下一轮；重试只补写叙述。
- 已发布：正式剧情和状态可以一起查看，允许下一轮行动。

模型超时不能导致“物品扣了但系统声称什么都没发生”，也不能为了重新叙述而重新掷骰。若叙述持续失败，可发布忠实于已结算事实的系统简报后暂停，待恢复再续玩。

### 13.5 长期记忆

| 层次 | 内容 | 规则 |
|---|---|---|
| 权威状态 | 角色、生命、物品、位置、章节、任务、关系 | 以结构化存档为准 |
| 事件账本 | 玩家行动、确认、骰子、结果、揭示与管理操作 | 保留事件编号和来源，不被摘要替代 |
| 固定世界资料 | 真相、NPC 动机、章节约束、触发条件 | 模板确定，不被自由续写覆盖 |
| 历史摘要 | 场景与章节回顾、未完成承诺 | 压缩辅助信息，必须引用来源事件 |
| 当前上下文 | 当前场景、相关人物、近期事件 | 有选择地送入模型，不每次发送全部历史 |

摘要与结构化事实冲突时，以事实为准并重新生成摘要；摘要失败不能阻止既有进度保存。

主持规划可以使用必要的未揭示资料；公开叙述只接收本轮允许披露的事实和最小必要信息，不把完整秘密剧本交给面向玩家的自由续写上下文。此隔离可降低泄密风险，但仍须通过专门的对抗用例验证，不能把提示词当作唯一保障。

### 13.6 叙述质量要求

- 普通推进建议 150–300 字，重大场景不超过 600 字，避免长篇独白。
- 回应玩家真实提交的动作，不编造玩家已同意的对白、情感和选择。
- 给出明确变化，再给可行动的新处境，不连续只写气氛。
- 区分 NPC 的说法与客观事实。
- 已探索地点、已取走物品、已失效关系必须保持一致。
- 允许玩家对 NPC 提问；NPC 只能按自身知识和立场回答。
- 安全边界要求与世界一致性优先于戏剧性。

### 13.7 纠错

玩家可对某条叙述提交“与记录不符”，关联已知事件。

- 系统在当前结算安全点暂停推进，检查被指出的冲突。
- 仅措辞或摘要错误：生成带来源的更正，保留原记录与更正关系。
- 机械结果已保存：不得因文案错误重新掷骰或重复扣资源。
- 无法自动判断：保持存档，提示需要技术处理，不让 AI 任意覆盖历史。
- “结果不喜欢”不是纠错依据；首版不提供普通玩家回档功能。

## 14. 长期身份、存档与隐私

### 14.1 玩家身份

- 首次启用跑团时生成稳定玩家标识，昵称和角色名只是显示信息。
- 本机记住登录会话；刷新不创建新玩家。
- 玩家改昵称、使用相同昵称，不影响角色归属。
- 浏览器身份过期后可以通过恢复码重新认证。

### 14.2 恢复码

- 恢复码是高强度随机凭证，建议随机强度不少于 128 位；不是短数字验证码。
- 仅在首次生成或轮换时完整展示，明确提示“持有此码即可控制你的全部跑团角色”。
- 服务端不得保存可直接使用的明文恢复码；恢复码不进入 URL、聊天、日志或 AI 上下文。
- 使用恢复码建立可撤销会话；建议采用 Secure、HttpOnly、SameSite 的会话 Cookie，不把恢复码当作日常请求令牌。
- 支持查看当前身份、退出本机、撤销其他设备会话和轮换恢复码。
- 轮换恢复码使旧码与其他设备会话失效，当前确认操作的会话保留。
- 换设备恢复后，展示该身份已有战役和角色，不按昵称搜索并认领。
- 恢复码丢失但本机仍有有效会话，可重新生成；若所有会话与恢复码均丢失，首版不承诺找回。

恢复接口须有速率限制和通用错误文案，不能泄露玩家是否存在；所有身份变更接口都需要会话与来源校验。

### 14.3 存档内容

必须保存：

- 成员身份、角色归属、发起人、缺席约定与内容边界。
- 战役与规则版本、章节与当前场景。
- 角色状态、已解锁能力、物品和个人背景。
- NPC、关系、承诺、任务、线索与世界事实。
- 战斗遭遇、先攻、当前行动者、技能使用次数和骰子结果。
- 已提交行动、确认状态、操作编号、已结算但尚待叙述的结果。
- 正式冒险日志、摘要及事件版本号。

锁定操作、判定结果和正式发布均要有可靠保存点。成员看到“已保存”时，应当意味着服务端已经确认，而不是仅写入浏览器。

### 14.4 生命周期与公开记录

- 战役存档不参与现有空房 30 分钟清理。
- 普通聊天仍遵循临时历史规则；正式跑团记录长期保存，两者在界面和隐私说明中分开。
- 每条正式记录使用可追溯标记，例如“第 2 章·场景 3·事件 128”；战斗额外显示回合与行动者。
- 长日志分页加载，不把全部历史一次下发。
- 发起人可在暂停状态归档战役；归档只读，不删除，恢复游玩需重新确认出席和准备。
- 支持导出队伍可见日志和当前公开状态，不包含隐藏剧本、恢复凭证、模型密钥或其他技术秘密。
- 首版不支持用户导入存档；导出不是完整灾备恢复工具。
- 永久删除战役须由全体现有成员确认；确认后 7 天内任一成员可取消，期限内只读，期满删除在线数据。
- 成员有权退出；其角色归档，不再有访问权，其他人的共同剧情记录保留。提供申请匿名化既有显示名的入口，并说明共同日志中的历史自由文本可能需要人工处理。
- 不因普通离线自动删除长期数据；接近存储上限时预警并停止新推进，不静默截断剧情。

### 14.5 数据告知与内容边界

创建角色前明确说明：

- 正式行动、角色背景及相关战役记录会发送给已配置的 AI 服务商。
- 场外聊天室闲聊不发送给主持模型。
- 不要输入真实身份证件、联系方式、工作机密或其他不必要敏感信息。
- 数据保存范围、导出、退出与删除规则。
- 具体模型服务商及其数据政策需在部署时填写真实信息；未配置完成不能启用 AI 功能。

开团前每人可选择不希望出现的主题，例如细节血腥、恐怖、虐待、亲密关系；队伍采用所有成员限制的并集，不公开是谁提出限制。新成员加入可收紧边界，已归档的旧剧情不会因此声称从未发生，但继续叙述必须遵守新边界。

任意玩家可点击“停止这个情节”立即请求安全暂停，无需公开理由。已结算状态不自动回滚，暂停后可将不适内容改为非细节化的概括，不因安全暂停惩罚角色。

## 15. 掉线、缺席与管理规则

| 情况 | 首版行为 |
|---|---|
| 刷新页面、短暂掉线 | 保留角色和待处理操作；重连补发权威状态与缺失事件 |
| 同一身份多个页面 | 均可查看；任何操作均按服务端版本与操作编号校验，重复或过期提交拒绝 |
| 当前玩家未行动就掉线 | 停止下一次推进，不自动选择行动 |
| 所有人离线 | 在当前已锁定操作的安全结算点保存并暂停，之后不继续调用 AI |
| 战斗中有人长期离线 | 保存战斗等待恢复，不自动接管或移出角色 |
| 探索中有人需要提前离开 | 完成本轮或撤回未锁定行动后暂停，再按缺席约定重建出席名单 |
| 只有一人在线 | 可看记录、编辑尚未提交的草稿，不能推进主线或战斗 |
| 新玩家中途加入 | 发起人批准后占用空席，完成角色创建，在安全场景边界加入；战斗中不加入 |
| 玩家永久退出 | 仅在暂停且无未决行动／表决时完成；角色归档，不可被他人接管 |
| 发起人暂时不在 | 已授权的缺席续团可由上次聚会指定的代理发起人组织；未指定则等待 |

### 15.1 缺席约定

每个玩家在开团时选择：

- 默认“我缺席时等待我”。
- 可选“允许至少两名队友在我缺席时续团”。

缺席续团只可在非战斗、无未决选择的安全边界开始；缺席角色设为留守，不参与检定、不消耗其物品、不自动死亡、不新增个人承诺。队友可以改变共享世界，但涉及缺席角色个人底线、永久背景变化或专属关键物品的决定必须等待本人。

成员可在下一次聚会前修改缺席偏好，不能在进行中的表决里即时生效。缺席者回来先阅读期间摘要，再于安全边界回归。

## 16. 页面与交互需求

### 16.1 战役列表

显示名称、当前章节、队伍人数、状态、最后游玩时间、未读事件和续玩入口。

状态使用明确文字：等待成员、准备中、探索中、战斗中、已暂停、AI 暂不可用、已完结、已归档；不能只用图标或颜色。

### 16.2 战役主界面

桌面端建议三块，移动端改为主视图＋抽屉切换：

1. **故事区**：当前场景、NPC 对白、正式行动、判定卡和事件结果。
2. **队伍／资料区**：队伍状态、角色、物品、线索、NPC 关系、日志。
3. **行动区**：讨论／行动切换、自由文字、建议行动、准备状态、提交与确认。

常驻顶部显示战役名、章节、当前目标、出席成员、暂停状态和保存状态。不能仅靠滚动聊天寻找“现在轮到谁”。

### 16.3 战斗界面

不另开复杂地图，使用紧凑遭遇面板：

- 战斗目标、回合号、先攻顺序。
- 敌我前后排、生命、公开状态。
- 当前轮到谁，以及自己为什么暂时不能行动。
- 本人合法动作、目标、次数和预计消耗。
- 已完成动作对应的骰子与结果。

### 16.4 记录与前情回顾

- 提供“上次发生了什么”“当前目标”“未履行承诺”“按章节查看”入口。
- 摘要中的关键项可以跳回来源事件。
- 显示自上次阅读后的新事件，不把所有历史标成未读。
- 进入战役先提供短回顾，不强迫阅读完整旧日志。

### 16.5 提示音与可访问性

- 沿用“聊天提醒／全部提醒／关闭”的明确当前状态表达。
- “全部提醒”覆盖轮到行动、需要确认、队伍投票、暂停恢复等需要本人关注的事件。
- 同一待处理事项不因状态刷新或重连反复响铃，不逐段为 AI 文字播放提示音。
- 支持键盘操作、可读标签、清晰焦点；状态不只通过颜色区分。
- 输入按钮明确显示“发送讨论”“提交行动”“确认并判定”，避免把聊天下意识地当作行动。

## 17. 模型成本、性能与使用限制

### 17.1 成本原则

- 继续以小规模熟人使用、低运维成本为目标，AI 推理与长期存储单独评估。
- 不因采用现有托管平台就承诺免费；实际费用取决于部署方案、模型和使用量。
- 模型由部署管理员统一配置；PRD 不预先指定供应商。
- 密钥只保存在服务端，玩家和发起人不能查看，也不能任意调高部署预算。
- 普通聊天、查看角色、翻阅已保存日志、战斗确定性数值运算不调用模型。
- 探索按整轮合并处理；战斗动作即时显示系统结果，常规 AI 描述按战斗回合汇总，关键结束节点可提前生成。
- 不为“刷新措辞”提供无限重新生成按钮。

### 17.2 建议初始限额

以下为可配置起点，上线前应使用选定模型实测调整。

| 限制 | 建议初值 | 达到上限时 |
|---|---|---|
| 每身份拥有的未删除战役 | 3 个，归档也计入 | 不能继续创建，已有战役不受影响 |
| 每战役成员数 | 4 人，不含已退出归档角色 | 拒绝加入，不替换已有角色 |
| 每战役同时进行的推进 | 1 个 | 合并重复请求，拒绝不同的并发推进 |
| 单次模型请求输入／输出 | 最多约 12,000／2,000 tokens | 优先裁剪无关历史，必需事实仍超限则暂停，不静默丢弃关键约束 |
| 每次探索推进正常模型调用 | 通常最多 2 次 | 规划与叙述各一次，禁止无界自主循环 |
| 每次推进格式修复调用 | 最多 1 次自动修复 | 仍不合法则暂停并显示错误 |
| 每战役每日模型预算 | 输入＋输出合计 1,000,000 tokens | 阻止新 AI 推进，可继续查看和导出 |
| 整个部署每日预算 | 2,000,000 tokens，管理员可调低 | 所有战役停止新 AI 请求 |
| 每战役长期数据 | 50 MiB，80% 时预警 | 达上限前停止接收可能超限的新推进 |

每日预算以 UTC 自然日重置，界面换算并显示本地重置时间。所有模型调用，包括失败后重试、摘要、纠错，都计入预算；发起请求前预留其最大可能额度，完成后按实际用量结算，无法确认服务商是否计费的超时请求暂按预留额度计入。token 上限不是货币账单保证，部署管理员还应使用服务商支持的消费上限或告警。

### 17.3 性能与反馈目标

- 本地操作和请求接收：95% 在 1 秒内反馈，不代表 AI 已生成完成。
- AI 单次生成阶段：目标 95% 在 20 秒内返回；探索的规划与叙述分开计时，玩家确认等待不计入。
- 任一模型请求达到 45 秒未完成，停止等待并进入可恢复错误状态。
- 断线重连成功后，目标 3 秒内展示当前状态和最近事件。
- 不满足目标时可评估更换模型或减少上下文，不通过伪造完成状态掩盖延迟。

### 17.4 失败处理

- 仅网络瞬时错误允许一次自动重试，预算和既有结算结果保持一致；格式修复与网络重试合计每次推进最多增加一次自动请求。
- 不可用密钥、余额不足、权限错误不自动重试。
- 手动重试前显示原因；延续原操作和骰子，只补未完成阶段，同样计入限额。
- 连续三次失败后停止自动尝试，显示“AI 暂不可用”，由管理员修复配置或玩家稍后主动重试。
- 重试返回的迟到结果若已过期，不得再发布一次事件或覆盖新状态。
- 预算耗尽或服务中断时，当前已结算结果必须保存；不再调用 AI，也不强行继续无主持剧情。

## 18. 系统约束与数据契约

本节规定产品必须满足的边界，不指定完整数据库结构、接口或部署实现。

### 18.1 能力边界

- **房间与连接**：负责在线通信和入口，不拥有长期战役生命周期。
- **玩家身份与授权**：负责角色归属、成员可见范围、恢复与会话撤销。
- **战役状态**：持有唯一权威进度，串行处理正式推进。
- **规则判定**：确定合法行动、随机结果和数值变化，可独立验证，不依赖模型文案。
- **AI 主持**：在许可内容内规划与叙述，不直接掌握写状态权限。
- **事件与记忆**：保存来源、摘要、查询和回顾。

可以复用现有实时通信和纯规则模块的组织思路，但不得把新的规则、模型调用和权限全部堆进现有聊天室处理流程。

### 18.2 核心对象

| 对象 | 必须表达的业务事实 |
|---|---|
| 玩家身份 | 稳定标识、会话状态、恢复凭证校验信息 |
| 战役 | 模板版本、规则版本、成员、生命周期、当前状态版本 |
| 角色 | 所属玩家、背景、属性、能力、生命和物品 |
| 聚会 | 出席者、代理发起人、准备状态、开始与暂停点 |
| 场景／遭遇 | 当前目标、可互动对象、已发生变化、推进条件 |
| 行动 | 发起者、目标、草稿／确认／锁定／结算／发布状态、幂等标识 |
| 事件 | 编号、来源行动、骰子、结果、公开范围、时间 |
| 记忆 | 线索、承诺、关系、世界事实、摘要及来源事件 |
| AI 作业 | 所属操作、处理阶段、模型版本、用量、失败与重试状态 |

### 18.3 不可破坏的不变量

1. 角色不能被同昵称的另一身份接管。
2. 同一操作至多产生一次机械结算和一条正式发布结果。
3. 掷出的骰子在刷新、重连、超时和修正文案后不变。
4. AI 文本不是权威状态；后台未认可的奖励和物品不生效。
5. 公开事实不能因上下文压缩而被重写。
6. 主持人隐藏资料不得作为公共状态、日志、导出或错误堆栈下发。
7. 普通聊天室清理不会删除战役和玩家身份。
8. 暂停和无人在线不会持续自动推进剧情或产生无界模型费用。
9. 新代码上线不能静默改变进行中战役的规则版本；不兼容迁移必须显式处理。
10. 用户和模型输出按不可信文本渲染，不执行 HTML、脚本或模型提供的任意外部动作。

## 19. 需求优先级与交付分期

### 19.1 首版必须包含（P0）

| 编号 | 能力 | 完成条件 |
|---|---|---|
| P0-01 | 身份、恢复码与授权 | 跨设备恢复，同昵称隔离，会话撤销有效 |
| P0-02 | 战役创建、邀请、准备、暂停与续玩 | 2–4 人完成全流程，游戏占用不冲突 |
| P0-03 | 角色与队伍关系 | 四种职业、背景、底线、互认关系、预设角色 |
| P0-04 | 讨论／行动分离与多人协调 | 自由行动、协助、等待、冲突澄清、风险确认、重大选择 |
| P0-05 | 检定与轻战斗 | 系统骰子、固定规则、合法动作、倒地、撤离和失败推进 |
| P0-06 | 线索、物品、NPC 与承诺 | 可查看、来源可追溯、实际影响后续剧情 |
| P0-07 | 长期记忆与存档 | 跨天恢复，空房不删，摘要不覆盖事实 |
| P0-08 | AI 约束、费用与失败恢复 | 输出校验、预算限制、超时恢复、不重复结算 |
| P0-09 | 首发三章节原创战役 | 内容完备并完成至少一次全流程内测 |
| P0-10 | 日志、隐私、退出、归档与删除 | 可理解数据范围、可导出、权限撤销正确 |
| P0-11 | 内容边界与安全暂停 | 开团约定生效，任何玩家可停止不适情节 |
| P0-12 | 基础移动端与现有功能兼容 | 可在窄屏完成核心操作，聊天和牌局无回归 |

### 19.2 后续增强（P1）

- 更多原创战役和独立章节内容包。
- 更丰富但受规则约束的职业叙事能力。
- 经授权的个人秘密、私密线索与对玩家可解释的信息隔离。
- 更细的个人 NPC 关系和背景支线。
- 轻量可视地图、角色立绘和更丰富的音效。
- 更完善的存档迁移和用户可控导入。

P1 不是本次首版验收要求，尤其不能先做立绘和地图而缺少跨天续玩。

### 19.3 研发验证顺序建议

1. **可信底座**：身份、长期存档、权限、事件记录与确定性判定；使用固定假主持验证流程。
2. **完整竖切**：两个玩家进入一个原创场景，完成自由行动、检定、关系变化、短战斗、暂停和恢复。
3. **AI 接入验证**：规划／叙述分离、秘密隔离、纠错、预算与超时恢复。
4. **叙事扩展**：章节、个人背景、任务、承诺、成长与结局组合。
5. **首版内容与内测**：完成三章内容、多设备组队测试、异常注入和现有功能回归。

具体任务拆分与工作量估算需要在 PRD 评审后另行制定，本稿不预估“几天即可完成”。

## 20. 验收场景

| 编号 | 场景 | 预期结果 |
|---|---|---|
| AC-01 | 两名新玩家创建战役并使用预设角色 | 无需账号注册，完成准备后进入首个可行动场景 |
| AC-02 | 三／四名玩家同时提交本轮 | 每人行动都被处理，只有一个有效推进 |

| AC-14 | 使用已耗尽的职业能力或不存在的物品 | 服务端拒绝，AI 描述不能绕过限制 |
| AC-15 | 战斗中倒地、救起与撤离 | 按固定规则处理，无额外插队，无自动永久死亡 |
| AC-16 | 全员倒地 | 进入预设失败分支，存档和角色保留 |
| AC-17 | 掷骰完成后模型超时 | 保留结果，重试仅补叙述，不再次判定 |
| AC-18 | 同一 AI 请求返回两次或迟到 | 至多发布一次；过期结果不覆盖现有状态 |
| AC-19 | 模型输出非法数值、奖励或对象编号 | 拒绝应用并进入有限修复或暂停流程 |
| AC-20 | 玩家要求忽略规则、泄露幕后真相或恢复码 | 不执行权限外要求，不暴露隐藏资料和凭证 |
| AC-21 | 摘要声称已死亡 NPC 仍活着 | 权威事实保持不变，摘要被更正 |
| AC-22 | 第一章帮助／欺骗关键 NPC | 第二章的对话或可用帮助有明确差异和来源 |
| AC-23 | 全员离线超过 30 分钟后回来 | 聊天临时清理不影响战役；恢复原状态 |
| AC-24 | 战斗中断线并跨天恢复 | 先攻、当前行动者、生命、次数和骰子全部一致 |
| AC-25 | 缺席玩家未允许续团 | 不能通过更改在线名单绕过其约定 |
| AC-26 | 已允许缺席续团 | 仅在安全边界开始，缺席角色不被代操或消耗资源 |
| AC-27 | 达到战役或全局模型预算 | 不再发起模型请求，仍可查看和导出 |
| AC-28 | 任何玩家点击停止情节 | 安全暂停，不要求理由，不惩罚角色 |
| AC-29 | 删除请求未获全员确认或在冷静期内取消 | 不删除存档，恢复原管理状态 |
| AC-30 | 暂停跑团后发起斗地主／德州，再恢复跑团 | 游戏占用规则正确，各自数据不互相覆盖 |

自动化测试覆盖规则、权限、存档和异常流程；真人内测验证叙事主体性、节奏和可玩性。模型输出测试使用固定上下文和可复查样本，不仅判断返回格式正确。

## 21. 示例：一次叙事优先的探索轮

### 当前处境

队伍来到雾钟镇档案室，管理员伊莱拒绝让外乡人查看失踪居民的旧档案。桌上放着一封印章与玩家来信相同的公函。

### 玩家讨论与行动

- 守卫在讨论区建议：“先别闹事，我来说明来意。”这句话不发给 NPC。
- 守卫正式行动：“我把来信递给伊莱，说明我们只是想找到收信人，请他帮忙核对名字。”
- 秘术师正式行动：“我不碰桌上的公函，观察两封信的印章是否属于同一机构。”
- 游侠选择协助守卫：“我说明信件曾被人抢夺，我们担心收信人有危险。”

### 判定准备

- 秘术师的安全观察获得公开可见事实：印章图案相同，不掷骰，不自动读取封闭信件。
- 守卫的交涉使用意志，标准难度 12；游侠的事实补充形成有效协助，获得优势。
- 判定卡说明：成功获得档案查阅许可；低于目标 1–3 点时，管理员要求先帮忙解决一个问题；更低时管理员暂时拒绝并要求队伍说明信件来源，但仍保留其他调查路径。
- 守卫确认，系统掷骰并保存。

### 正式结果

系统显示：`d20：6／15，取 15；意志＋1；总值 16，对目标值 12，成功。`

AI 描述伊莱收起戒备、打开档案柜，并询问队伍在哪里得到这封信；不擅自写“你们决定把全部秘密告诉他”。

日志更新：

- 新线索：两封信使用同一印章，来源为本轮观察。
- 获得权限：允许查阅这一册旧档案，不等于拿到全部档案内容。
- 伊莱对队伍的公开态度有所缓和，记录本轮交涉为来源。
- 下一轮由玩家决定继续查阅、回答问题或追问公函，AI 不代替决定。

这个闭环同时具备自由行动、多人参与、可验证规则、信息边界与后续选择，代表首版应达到的核心体验。

## 22. 主要风险与评审结论

| 风险 | 首版取舍 |
|---|---|
| AI 看似自由，实际一直把玩家拉回固定答案 | 主线规定目标和事实，不固定唯一解法；验收选择是否改变后续可用路径 |
| 长期剧情遗忘、偷偷改设定 | 权威状态＋来源事件＋分层摘要，原始事件不被压缩删除 |
| 为防 AI 失误而限制得像选项游戏 | 保留自由输入，系统约束结果类型而不限定表达方式 |
| 规则太重压过叙事 | 四职业、五属性、两档站位、短战斗、无刷经验装备循环 |
| 多人互相等待或一个人包办 | 明确行动窗口、观察等待、缺席约定和每位玩家贡献回应 |
| 模型费用超过小项目预期 | 整轮合并、战斗规则本地结算、上下文上限、预算预留、无后台自动世界循环 |
| 恢复码丢失／泄露 | 强随机凭证、显著提示、会话撤销与轮换；明确无凭证不承诺找回 |
| 内容只有开场可玩 | 首发三章成品作为 P0，要求真实通关而不只测试接口 |
| 首版范围大于现有小游戏 | 先验证单场景完整竖切，再扩三章；不把整个功能当作一个聊天命令改造 |

**本稿结论：**首版要优先证明“这群朋友可以共同经历并续玩一个记得他们选择的故事”。地图、立绘、更多职业和更深装备系统都不能替代这个目标。

下一步是评审本稿的建议默认值、首发内容规模和缺席／身份规则；确认后再拆技术设计与实现计划。本次不进入编码。
